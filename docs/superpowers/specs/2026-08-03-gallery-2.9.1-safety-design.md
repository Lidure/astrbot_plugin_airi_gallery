# Airi Gallery v2.9.1 Safety Design

## Goal

Complete the v2.9 local-deletion synchronization feature without adding broad new product features. The patch must close permission and remote-deletion safety gaps, preserve existing installations, add regression tests, and make help command aliases consistent.

## Scope

### 1. Permission Evaluation

Management commands continue to use the existing `use_permission`, `admins`, and `whitelist` configuration fields.

Add a pure helper that reads boolean event flags safely:

- A boolean attribute is used directly.
- A synchronous callable is called and its returned value is converted to `bool`.
- A missing attribute, exception, or awaitable result is treated as `False`.

`_is_allowed()` uses this helper for both `event.is_admin` and `sender.is_admin`. It also recognizes `event.is_master` with the same rules. A bound method must never grant permission merely because the method object is truthy.

The `use_permission` default remains `false` in this patch to avoid silently locking existing users out. Configuration hints and README text will clearly recommend enabling it in shared groups.

### 2. Verified Remote Baselines

The hash index is upgraded from schema version 1 to schema version 2. Existing fields remain valid and each file entry may additionally store:

- `git_blob_sha`: Git blob SHA-1 calculated from the local file bytes.
- `remote_sha`: the remote blob SHA last proven to represent the same bytes as the local file.

An entry is a verified remote baseline only when `git_blob_sha` and `remote_sha` are both non-empty and equal.

A baseline may be recorded only after one of these events:

1. A remote file is downloaded successfully and written locally.
2. A local file is uploaded successfully and the resulting blob SHA is known.
3. A sync or push scan calculates the local Git blob SHA and proves it equals the current remote tree SHA.

A matching file size alone is not proof of identical content and must not create a verified baseline.

Version 1 index entries are loaded without destructive migration. They remain usable for SHA-256 duplicate detection, but they have no verified remote baseline until a later sync or push proves byte equality.

### 3. Safe Local-Deletion Preview

Remote deletion candidates must satisfy every condition below:

- The path is a supported image below `gallery/<category>/`.
- The local path no longer exists.
- The path has a hash-index entry.
- The index entry contains a verified remote baseline.
- The current remote tree SHA equals the stored `remote_sha`.

Candidate discovery returns a structured report containing:

- safe candidates;
- files skipped because no verified baseline exists;
- files skipped because the remote SHA changed.

The preview response tells administrators how many files were skipped for each safety reason. If only unverified files exist, it instructs the administrator to run `/立即同步` or `/推送到远程` first. No command may automatically weaken this rule.

Confirmation keeps the existing five-minute expiry and exact-count requirement. It fetches the remote tree again and rejects an item if the local file reappeared or the remote SHA changed after preview. Successful deletion removes the corresponding hash-index entry.

### 4. Baseline Persistence

Hash-index writes remain atomic through the existing temporary-file replacement. Updating baseline metadata must preserve SHA-256, size, modification time, and category fields.

The following flows persist verified baselines:

- GitHub batch pushes;
- GitHub or Gitee individual pushes;
- files skipped during fast push because local and remote Git blob SHAs match;
- files downloaded during remote synchronization;
- existing local files verified against the remote tree during synchronization.

If an upload succeeds but the API does not provide a resulting SHA, the plugin may calculate the local Git blob SHA but must leave `remote_sha` unverified until a later remote-tree check.

### 5. Help Alias Consistency

The following commands all open the same help flow:

- `/airi_gallery`
- `/画廊帮助`
- `/图库帮助`

Both decorated command handlers and the central parser recognize the aliases. Help text and README list the Chinese aliases consistently. Existing aliases remain compatible.

### 6. User-Facing Documentation

Release version becomes `v2.9.1` in `metadata.yaml` and the README badge and changelog.

Documentation explains:

- permission control is strongly recommended in shared groups;
- old hash indexes need one successful sync or push before deleted files become eligible for remote deletion;
- same-size files are content-verified before a remote baseline is trusted;
- local-deletion preview reports unsafe or changed remote files as skipped.

No new runtime configuration fields or third-party dependencies are added.

## Architecture

Create `gallery_safety.py` as an AstrBot-independent module. It owns:

- safe boolean flag evaluation;
- Git blob SHA calculation;
- hash-index v1-to-v2 normalization that preserves legacy entries;
- pure remote-deletion candidate selection.

`main.py` remains the integration layer for AstrBot events, filesystem access, Git API calls, messages, and locks. Pure safety decisions are delegated to `gallery_safety.py`, allowing tests to run without installing or importing AstrBot.

Candidate selection consumes plain dictionaries plus a callable that reports whether a local path exists. It returns a typed report or an equivalent immutable data object. It performs no network, filesystem mutation, or message sending.

## Error Handling

- Malformed hash-index entries are ignored or normalized conservatively; they never become verified baselines.
- An unreadable hash index starts as an empty v2 index and logs a warning.
- Network or tree-list failure produces no deletion candidates and performs no deletion.
- Failure to calculate a local blob SHA leaves the entry unverified rather than falling back to file size.
- Index persistence failure is logged and leaves remote deletion unavailable for affected files on the next process start.
- Detailed token values and repository credentials are never included in messages or logs.

## Compatibility

- Existing gallery files and configuration are not renamed or moved.
- Existing version 1 hash entries continue accelerating duplicate detection.
- Existing browse, upload, deduplication, LLM, GitHub, Gitee, and Cloud page behavior remains unchanged except for stricter deletion eligibility.
- Users who never enable Git synchronization see no behavioral change.
- Users with unverified legacy deletions receive a safe instruction instead of an actionable deletion preview.

## Testing

Add pure `pytest` tests that do not import AstrBot:

- boolean attributes, callable flags, false-returning methods, exceptions, and awaitable-returning callables;
- Git blob SHA compatibility with known byte payloads;
- schema v1 entries preserve duplicate-detection data but remain unverified;
- schema v2 verified baseline detection;
- candidate acceptance only when local absence and both SHAs match;
- rejection for local reappearance, missing baseline, changed remote SHA, invalid path, and unsupported extension;
- deterministic candidate ordering and skip counts.

Add static repository checks for:

- Python AST compilation;
- JSON parsing of `_conf_schema.json`;
- YAML-readable metadata;
- version consistency across `metadata.yaml`, the README badge, and the README changelog;
- all three help aliases appearing in parser/help documentation.

GitHub Actions runs these checks on pushes and pull requests with Python 3.10 and 3.12. Test-only dependencies are installed by the workflow and are not added to the plugin runtime requirements.

## Acceptance Criteria

- A false-returning `event.is_admin()` method does not grant management permission.
- A true boolean or true-returning synchronous admin/master method grants permission when permission control is enabled.
- A missing `remote_sha` prevents a deleted local file from entering the remote deletion preview.
- A current remote SHA different from the stored baseline is reported as changed and cannot be deleted.
- A successful verified sync or push stores the baseline atomically and subsequently permits a genuinely unchanged local deletion to be previewed.
- Confirmation still requires the exact count within five minutes and revalidates local existence and remote SHA.
- All existing and new tests pass on Python 3.10 and 3.12.
- The working tree contains no generated caches or credentials.
